## Speed audit vs Moving 30A (Lighthouse mobile, simulated, same box)

| | BHM | Moving 30A |
|---|---|---|
| Performance | **66** | **93** |
| LCP | **9.1 s** | 2.6 s |
| FCP | 2.0 s | 2.0 s |
| TBT | 300 ms | 150 ms |
| CLS | 0 | 0.002 |
| TTFB | 50 ms | 70 ms |

Diagnosis: the entire gap is the hero. SSR HTML ships the H1 (and hero copy) at `opacity:0`
(framer-motion initial state inside the dynamically-imported `HeroMotionLayer`), so the largest
paint waits for JS download → hydration → dynamic chunk → animation (some elements delay 1.5 s).
TTFB/FCP are already competitive; hero image is `priority` and only 50 KB — not the problem.

Recommended fixes (none shipped yet — Travis to approve):
1. **Hero text server-visible + CSS entrance** (the fix that closes the gap): move headline/subhead/CTA
   markup out of `HeroMotionLayer` into server-rendered JSX; animate with a CSS `fadeUp` keyframe
   (runs before hydration). Keep framer for parallax/floating badges. Expected: LCP ~2.3–2.6 s,
   score ~90 — Moving 30A parity. Purely presentational, no logic touched.
2. Optional: GTM `strategy="afterInteractive"` → `lazyOnload` (–305 KB off critical path, TBT down).
   Tradeoff: pageview fires later; very-fast bounces may go uncounted. Lead events (form/phone) unaffected.
3. Minor: `circular-logo.png` (75 KB, 1024²) is fetched as icon on every load — add a 192² variant
   for the manifest/icon slot, keep 1024² only as the hi-res manifest entry. ~60 KB saved.
