## Speed audit vs Moving 30A (Lighthouse mobile, simulated, same box)

| | BHM | Moving 30A |
|---|---|---|
| Performance | **66** | **93** |
| LCP | **9.1 s** | 2.6 s |
| FCP | 2.0 s | 2.0 s |
| TBT | 300 ms | 150 ms |
| CLS | 0 | 0.002 |
| TTFB | 50 ms | 70 ms |

Diagnosis: the entire gap is the hero. SSR HTML ships the H1 (and hero copy) at `opacity:0`
(framer-motion initial state inside the dynamically-imported `HeroMotionLayer`), so the largest
paint waits for JS download → hydration → dynamic chunk → animation (some elements delay 1.5 s).
TTFB/FCP are already competitive; hero image is `priority` and only 50 KB — not the problem.

## Speed fixes SHIPPED (same night, Travis approved)

- **`a6c3cbc`** — hero copy now server-renders inside `HeroSection` and animates with CSS
  keyframes (`.hero-fade-up` / `.hero-slide-up` in `globals.css`), so the text paints before any
  JS runs. `HeroMotionLayer` keeps only parallax, scroll progress, floating cards, scroll cue.
  Two Chrome LCP heuristics were load-bearing: text animated from `opacity: 0` is dropped as an
  LCP candidate entirely, so the fades start at `0.01`, and the H1 uses a transform-only slide.
  Tab icon: browsers fetched the 75 KB 1024² logo per page; icon link now = 15 KB 192² variant
  (`icon-192.png`), big sizes remain in `manifest.ts` for PWA install.
- **`ae51ee3`** — GTM + Ahrefs moved `afterInteractive` → `lazyOnload`. Their ~300 KB eval was
  running before first paint under load. `gtag.ts` creates the `dataLayer` stub on every push,
  so events queue and drain when the container loads; `generate_lead`/`phone_click` fire long
  after load and are unaffected. Verified live: GTM absent at load, loaded at idle,
  `gtm.js/dom/load` all in the dataLayer. Known tradeoff: instant bounces may not log a pageview.
- **robots.txt** — removed `Disallow: /_next/` (audit §3 item 7): it hid CSS/JS from Googlebot's
  renderer, so Google scored every page unstyled. `/api/` stays disallowed.
